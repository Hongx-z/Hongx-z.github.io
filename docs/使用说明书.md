## 0. 这个网站是怎么组织的

网站分两大块，彼此独立，互不影响：

| 板块 | 网址 | 内容形式 | 数据来源 |
| --- | --- | --- | --- |
| **关于我**（About me） | `/about` | 文字 | `content/pages/about.md` + `src/data/resume.ts` |
| ↳ 文章列表 | `/writing` | 文字 | `content/articles/*.md` |
| ↳ 文章详情 | `/writing/<文件名>` | 文字 | 同上 |
| ↳ 标签分类 | `/tags`、`/tags/<标签>` | — | 自动从文章 + 纪录片里汇总 |
| **关于别人**（About others） | `/documentaries` | 视频 | `content/documentaries/*.md` |
| ↳ 纪录片详情 | `/documentaries/<文件名>` | 视频 | 同上 |
| 留言板 | `/guestbook` | 访客留言 | GitHub Discussions（见 9.1） |
| 版权页（半隐藏） | `/colophon` | 文字 | `content/pages/colophon.md`（见 9.4） |

**最重要的一条设计原则：所有内容都是文件。**

- 文章是一堆 `.md` 文件，一篇一个文件
- 纪录片是一堆 `.md` 文件，一部一个文件（`videoUrl` 里填视频链接）
- 经历和荣誉是两个数组，写在 `src/data/resume.ts` 里
- 你的名字、头衔、导航、社交链接，写在 `src/data/site.ts` 里

没有数据库，没有后台，没有登录。改文件 = 改网站。

技术上它是 **Next.js 的静态导出**：构建时把所有页面提前生成成纯 HTML/CSS/JS 文件，放到一个 `out/` 目录里。GitHub Pages 只是把这个目录当普通静态文件托管，所以**免费、无服务器、不会挂**。

## 1. 准备环境（只做一次）

### 需要什么

**Node.js 20.9 或更高版本**（推荐 22）。这是唯一的前置条件。

检查是否已安装：

```bash
node -v
```

如果显示 `v22.x.x` 之类就够了。如果提示「不是内部或外部命令」，去 <https://nodejs.org> 下载 LTS 版安装。

### 安装依赖

在项目目录里（有 `package.json` 的那一层）执行：

```bash
npm install
```

只需要做一次。以后只有在 `package.json` 变化时才需要重跑。

> 首次安装会下载一百多个包，视网络情况需要几分钟。装完会多出一个 `node_modules/` 目录 —— 那个目录**不要提交到 git，也不要手动改**，`.gitignore` 已经把它排除了。

## 2. 本地运行：改完立刻看到效果

```bash
npm run dev
```

看到这样的输出就成功了：

```
▲ Next.js 16.3.5
- Local:  http://localhost:3000
✓ Ready in 1.9s
```

浏览器打开 <http://localhost:3000>。

**这是写内容时最常用的模式。** 它的特点是：

- **热更新**：你保存文件，浏览器里的页面自动刷新，通常一两秒内
- **草稿可见**：frontmatter 里写 `draft: true` 的内容，在这个模式下**能**看到，但正式构建时不会出现
- **报错直接显示在页面上**：frontmatter 写错了会看到红色错误，并告诉你哪个文件

停止服务：在终端按 `Ctrl + C`。

换端口（默认 3000 被占用时）：

```bash
npm run dev -- -p 4321
```

> 这个模式适合边写边看，**但它不是最终产物**。要确认「发布出去长什么样」，必须走下一节的构建。

## 3. 构建与 out 目录（重点）

### 3.1 `npm run build` 做了什么

```bash
npm run build
```

这一条命令依次做了四件事：

1. **类型检查**：检查所有 TypeScript 代码。有错就停下，并指出文件和行号。
2. **读取全部内容**：扫描 `content/` 下的每个 `.md`，解析 frontmatter。**缺 `title` 或 `date` 会直接失败**，错误信息里带文件名。
3. **预渲染所有页面**：把每一篇文章、每一部纪录片、每一个标签页都提前渲染成完整的 HTML。
4. **输出到 `out/`**：把 `out/` 整个目录重建成最终的静态网站。

成功时的输出长这样：

```
✓ Compiled successfully
✓ Generating static pages (31/31)
Route (app)
┌ ○ /
├ ○ /about
├ ○ /writing
├   /writing/[slug]
│ ├ ● /writing/the-last-shift
...
```

`○` 是固定页面，`●` 是由内容生成的页面。**这里列出的每个地址，发布后都真实存在。**

### 3.2 `out/` 里面有什么

```
out/
├── index.html                        首页
├── 404.html                          404 页面
├── about/index.html                  关于我
├── writing/
│   ├── index.html                    文章列表
│   └── the-last-shift/index.html     一篇文章（一个目录一个页面）
├── documentaries/                    纪录片，结构同上
├── tags/                             标签页
├── sitemap.xml                       给搜索引擎的站点地图
├── favicon.svg                       站点图标
├── .nojekyll                         ← 重要！不要删
└── _next/                            样式表、JS、字体等
```

两个要注意的点：

- **每个页面是一个目录里的 `index.html`**，所以网址 `/writing/the-last-shift/` 带结尾斜杠，这是正常的。
- **`.nojekyll` 文件必须存在。** GitHub Pages 默认会忽略以下划线开头的目录，而 `_next/` 正是下划线开头 —— 少了这个文件，部署后网站会完全没有样式。它是 `public/.nojekyll` 复制过来的，别动。

### 3.3 本地预览 `out/`（确认发布效果）

```bash
npm run preview
```

然后打开 <http://localhost:3000>。这时你看到的是**真正会被发布的文件**，和 `npm run dev` 的渲染结果可能有一点点差别（比如草稿不显示了）。

换端口：

```bash
npm run preview -- --port 4000
```

想停掉：`Ctrl + C`。

### 3.4 关于 BASE_PATH（部署到子路径时必须知道）

这是静态网站部署**最容易出错**的地方，值得单独讲。

GitHub Pages 有两种仓库：

| 仓库名 | 网址 | 需要 BASE_PATH |
| --- | --- | --- |
| `<用户名>.github.io` | `https://h-zhu.github.io/` | 不需要（空） |
| 其他任意名字，如 `personal-site` | `https://h-zhu.github.io/personal-site/` | 需要 `/personal-site` |

**为什么**：第二种情况下，网站的所有文件实际都在 `/personal-site/` 这个子目录下。如果 HTML 里写着去 `/favicon.svg` 找图标，浏览器会去 `https://h-zhu.github.io/favicon.svg` 找 —— 找不到，于是样式、图标、图片全部失效。

`BASE_PATH` 就是告诉构建工具：「把 `/personal-site` 这个前缀加到所有资源地址前面」。

本地想验证子路径构建：

```bash
# macOS / Linux
BASE_PATH=/personal-site npm run build
BASE_PATH=/personal-site npm run preview

# Windows PowerShell
$env:BASE_PATH="/personal-site"; npm run build
$env:BASE_PATH="/personal-site"; npm run preview

# Windows CMD
set BASE_PATH=/personal-site && npm run build
```

**但你不需要手动设**：`.github/workflows/deploy.yml` 里的「Work out the base path」这一步会自动判断仓库名并设置正确的值。你只要正常推送就行。

### 3.5 ⚠️ 不要双击打开 `out/index.html`

浏览器地址栏直接打开本地文件时，路径是 `file:///...`，而页面里的资源路径是 `/..._next/xxx.css` 这种**绝对路径**。浏览器会去「硬盘根目录」找样式表，找不到。

结果就是：**白底黑字、完全没样式的裸 HTML**。

这不是网站坏了，是打开方式不对。永远用 `npm run preview` 看构建产物。

## 4. 内容编辑手册

### 4.1 站点信息与你的身份

**文件：`src/data/site.ts`**

这是打开的第二个文件（第一个是下面 4.2 的 about.md）。里面的每一项都有注释。

```ts
// 你的身份 —— 这是一个数组
export const roles: string[] = ['Writer', 'Documentary filmmaker'];

export const site = {
  name: 'H. Zhu',                    // 你的名字，出现在页头和浏览器标签
  tagline: roles.join(' · '),        // 自动由上面的数组拼出来，不用改这行
  roles,                             // 让页面能单独渲染每一项
  description: '...',                // 搜索引擎和分享卡片上的简介
  intro: '...',                      // 首页那句话
  url: 'https://...',                // 部署后的正式网址，见 6.4
  email: 'you@example.com',
  location: 'Your City',
  links: [                           // 页脚的社交链接，不要的整行删掉
    { label: 'GitHub', href: 'https://github.com/username' },
    { label: 'Email', href: 'mailto:you@example.com' },
  ],
  nav: [                             // 顶部导航，改 label 就改文字
    { label: 'About me', href: '/about' },
    { label: 'Writing', href: '/writing' },
    { label: 'Tags', href: '/tags' },
    { label: 'About others', href: '/documentaries' },
  ],
  filmChannelUrl: '',                // 填上视频频道地址，片子页会多一个外链
} as const;
```

**关于「身份不仅限于作家和制作人」—— 这里就是答案。**

`roles` 被设计成一个数组，就是为了不把你钉死在某两个头衔上。以后你做了别的事情，加一项即可：

```ts
export const roles: string[] = [
  'Writer',
  'Documentary filmmaker',
  'Radio producer',       // 新加一行
];
```

页头、浏览器标题、分享卡片会立刻全部跟着变。不需要改任何其他文件。

### 4.2 关于我：正文

**文件：`content/pages/about.md`**

`---` 之间的部分是「页头」，下面是正文。

```markdown
---
title: About me                   # 页面大标题
headline: >-                      # 大标题下面那句话，也就是你的自我介绍
  I write and I film. Those are not the only two things I do...
location: Your City
email: you@example.com
# portrait: /images/portrait.jpg  # 想放照片就取消这行注释
status:                           # 页头下面那几个小标签
  - Available for commissions
  - Currently filming
---

正文从这里开始，用 Markdown 写。
```

**`headline` 就是身份的正式表述**，可以写成完整的句子，不像 `roles` 那样受限于短词。想彻底重写自我介绍，改这里。

正文里 `##` 开头的行是小标题。照片放在 `public/images/` 里，然后在 `portrait` 里写 `/images/文件名.jpg`。

### 4.3 关于我：经历时间线

**文件：`src/data/resume.ts` 里的 `timeline` 数组**

这才是「按时间线记录做过的事情」的主体。`/about` 页面中间那一段。

```ts
{
  id: 'staff-writer',            // 随便一个不重复的字符串
  kind: 'work',                  // 'work' | 'education' | 'project' —— 决定小圆点的样式
  start: '2019-03',              // 'YYYY-MM'，只写年份 'YYYY' 也可以
  end: '2022-03',                // 不写这一行 = 一直持续到现在，会显示 Present
  title: 'Staff Writer',         // 加粗的大标题
  org: 'A Publication',          // 机构名
  location: 'Somewhere',         // 地点，和 org 用 · 连起来显示
  summary: '一两句话说明你做了什么。',
  highlights: [                  // 可选的要点列表，删掉这个字段就不显示
    '具体成果一',
    '具体成果二',
  ],
  tags: ['essay', 'reportage'],  // 可选；能点，跳到对应标签页
}
```

**几条实用规则：**

- **顺序就是显示顺序**，把最新的写在最上面（文件里注释也写了）
- `kind` 只影响左侧小圆点的颜色（`work` 是实心主题色，其他是空心）—— 想加新类型，改这里和 `src/components/Timeline.tsx` 里的 `KIND_LABEL`
- 完全没有经历要写，就把整个数组清空成 `export const timeline: TimelineEntry[] = [];`，页面会显示一个空状态提示，不会报错
- `end` 不写 = 至今，例如：

```ts
{
  id: 'current',
  kind: 'work',
  start: '2024-01',
  // 没有 end，就会显示 "Jan 2024 — Present"
  title: 'Independent work',
  summary: '...',
}
```

### 4.5 文章

**目录：`content/articles/`**，一篇一个 `.md` 文件。

**文件名就是网址。** `content/articles/the-last-shift.md` → `/writing/the-last-shift/`

建议文件名用小写英文 + 连字符（`my-first-post.md`），虽然中文文件名技术上可行，但网址里会出现一堆百分号编码，很难看。

最省事的做法：**复制 `content/articles/_TEMPLATE.md`，改名，照着里面的注释填。**

```markdown
---
title: The Last Shift
date: '2025-11-18'
summary: >-
  一两句话，会出现在列表、搜索结果和分享卡片里。不写的话自动截取正文前 180 字。
tags:
  - Reportage
  - Night Work
# cover: /images/cover.jpg
# draft: true
---

正文第一段。文章的第一段会做首字下沉处理。

## 一个小标题

两个以上的 `##` 小标题，宽屏下左边会自动出现目录。
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `title` | **是** | 缺了构建会失败，错误信息里带文件名 |
| `date` | **是** | `YYYY-MM-DD`，决定排序（新的在前）和显示 |
| `summary` | 否 | 不写则自动截取正文 |
| `tags` | 否 | 你自己的词，随意起 |
| `cover` | 否 | 头图，文件放 `public/images/` |
| `draft` | 否 | `true` = 本地能看到，正式构建时隐藏 |

**关于标签**：标签不需要预先定义，是从所有内容里自动汇总的。`Field Notes` 和 `field-notes` 会被认成同一个标签，所以大小写和空格不用纠结。

**关于草稿**：`draft: true` 是「先写着，别发」的正确做法。本地 `npm run dev` 能看到，`npm run build` 不会包含它，推送到 GitHub 也安全。

### 4.6 纪录片

**目录：`content/documentaries/`**，一部一个 `.md` 文件。

同样：**复制 `_TEMPLATE.md` 改名最省事。**

```markdown
---
title: The Water Reader
subject: Idris                 # 必填！片子拍的是谁
date: '2025-07-12'
location: An upland catchment
runtime: 22 min
summary: 一两句话。
tags:
  - Portrait
featured: true                 # 可选，加了会排在网格最前面
videoUrl: https://vimeo.com/123456789
# poster: /images/still.jpg
credits:
  Director & Camera: H. Zhu
  Sound: A Collaborator
---

## Director's note

导演阐述，用 Markdown 随便写。会显示在播放器下面。
```

#### `videoUrl` 支持哪些链接

**把链接粘进去就行，网站自己识别：**

| 你填的 | 效果 |
| --- | --- |
| `https://www.youtube.com/watch?v=XXXXXXXXXXX` | YouTube 播放器（用的是隐私增强域名） |
| `https://youtu.be/XXXXXXXXXXX` | 同上 |
| `https://vimeo.com/123456789` | Vimeo 播放器 |
| `https://www.bilibili.com/video/BV1xx411c7mD` | B 站播放器（弹幕已关） |
| `/videos/my-film.mp4` | 自带播放器，播放你放进 `public/videos/` 的文件 |
| **不填，或填了不认识的** | **不会报错**，显示一个设计过的占位画面，并提示你怎么填 |

最后一条很重要：**你可以先建好页面，视频以后再补。** 页面不会出现破图或者坏掉的播放器。

> 想自己托管视频文件的提醒：GitHub Pages 对仓库有约 1 GB 的软上限，也没有 CDN。超过一两分钟的片子，建议还是用 B 站 / YouTube / Vimeo，把链接填进来。

#### `poster`（封面图）

不填 `poster` 时，封面是根据文件名自动生成的一块渐变色块（所以每部片子的颜色都不同，不会看起来像一堆坏图）。有真实剧照了就放 `public/images/`，然后在 `poster` 里写路径 —— 16:9 比例最好看。

### 4.7 示例内容清单（发布前要替换掉的文件）

仓库里现在全是**示例内容**，作者名、机构名、文章都是编的。正式发布前，下面这些都要替换或删除：

| 文件 | 处理方式 |
| --- | --- |
| `content/pages/about.md` | 改成你自己的自我介绍 |
| `src/data/resume.ts` | `timeline` 和 `honors` 全部换成你的真实经历 |
| `src/data/site.ts` | 名字、`roles`、邮箱、城市、社交链接 |
| `content/articles/` 下 7 个 `.md` | **全部删掉**，换成你自己的文章 |
| `content/documentaries/` 下 5 个 `.md` | **全部删掉**，换成你自己的片子 |
| `_TEMPLATE.md`（两处） | **保留**，它以下划线开头，不会被发布，可以一直当模板用 |
| `public/favicon.svg` | 换不换都行，现在是一个中性的文字线条图标 |

删文章的方法就是直接删文件。删完之后「写作」页面会显示一个空状态提示，不会报错。

想看哪些文件是文章、哪些是纪录片，直接看目录名就知道了：

```
content/articles/          ← 文章
content/documentaries/     ← 纪录片
content/pages/about.md     ← 关于我页面的正文
content/pages/colophon.md  ← 版权页（第 9.4 节）
public/audio/              ← 背景音乐放这里（第 9.2 节）
```

## 5. 改外观

**只有一个文件：`src/app/globals.css`**

文件最开头是「设计变量」，改这里，全站跟着变：

```css
:root {
  --paper: #fbfaf7;        /* 页面底色（暖白） */
  --ink: #171614;          /* 正文颜色 */
  --ink-muted: #78736b;    /* 次要文字 */
  --accent: #9c4a2f;       /* 强调色：链接、标签悬停、时间线圆点 */
  --rule: #e4e0d8;         /* 分隔线 */

  --measure: 34rem;        /* 正文栏宽，约 68 个字符，别改太大 */
  --width-page: 68rem;     /* 页面整体宽度 */
}
```

**最常见的两个需求：**

换强调色 —— 把 `--accent` 改成一个色号即可，链接、标签、圆点、引用线会一起变。

```css
--accent: #1f5c4a;   /* 例如换成深绿 */
```

改字体 —— 现在是系统衬线字体（正文）搭配系统无衬线（界面文字），不依赖网络加载字体，打开很快。想换成 Google Fonts，在 `src/app/layout.tsx` 里用 `next/font` 引入，然后改 `--font-serif`。

> 注意：没有用 Tailwind 或任何 CSS 框架，就是普通的 CSS。类名都是 `timeline__entry`、`film-card__title` 这种可读的写法，直接搜就能找到。

## 6. 部署到 GitHub Pages

### 6.1 第一次：推上去

在项目目录里：

```bash
git init
git add .
git commit -m "Initial commit"
git branch -M main
git remote add origin https://github.com/<你的用户名>/<仓库名>.git
git push -u origin main
```

`<仓库名>` 随便起，比如 `personal-site`。**但仓库名会决定你的网址**，见下面 6.4。

### 6.2 开启 Pages（关键，只需一次）

打开仓库页面 → **Settings** → 左侧找到 **Pages** → 在 **Build and deployment** 的 **Source** 下拉框里选 **「GitHub Actions」**。

**就这一处设置。** 不要去选「Deploy from a branch」—— 那个方式需要我们手动构建、手动提交 `out/` 目录，很麻烦。选 GitHub Actions 之后，每次推送 GitHub 会自己帮我们构建并发布。

### 6.3 看第一次部署

点仓库顶部的 **Actions** 标签页。会看到一个叫「Deploy to GitHub Pages」的任务在跑，通常一两分钟。

- 绿色勾 = 成功，网址就在该任务页面里
- 红色叉 = 失败，点进去看日志。**最常见的原因是 `npm ci` 失败或 `npm run build` 类型检查不过**，日志会明确写出哪一行错了

### 6.4 网址怎么定的

| 仓库名 | 网址 |
| --- | --- |
| `personal-site`（普通仓库） | `https://<你的用户名>.github.io/personal-site/` |
| `<你的用户名>.github.io`（特殊仓库） | `https://<你的用户名>.github.io/` |

workflow 里的「Work out the base path」会自动判断这两种情况并设置正确的资源前缀 —— 这一步是绝大多数静态站部署翻车的地方，你不需要操心。

**部署成功后，回来改一行：** 打开 `src/data/site.ts`，把 `url` 改成你的真实网址，再推一次。

```ts
url: 'https://h-zhu.github.io/personal-site',
```

这一行只影响「规范链接」和分享到微信/推特时显示的卡片地址。不改网站也能看，但改了更规范。

### 6.5 以后每次修改

```bash
git add .
git commit -m "Add new article"
git push
```

推送完成 → 等一两分钟 → 刷新网址就能看到。**不需要手动构建，不需要手动上传 `out/`。** `out/` 是本地预览用的，加了 `.gitignore` 不会进仓库。

### 6.6 哪些文件会推送到 GitHub（`out/` 要不要推？）

**一句话：只推源码，`out/` 永远不推。**

原因是 `out/` 出现了两次，是两份不同的东西：

| 位置 | 谁生成 | 用途 |
|---|---|---|
| 你电脑上的 `out/` | 你手动跑 `npm run build` | 只给你本地预览用 |
| GitHub 上的 `out/` | GitHub Actions 在云端自动跑 `npm run build` | 真正被 Pages 发布的那个 |

你推的是**生成 `out/` 的原料**，GitHub 拿到原料后在云端重新生成一份自己的 `out/` 拿去发布。你本地的 `out/` 和线上的没有任何传递关系，所以推它不但没用，还会污染仓库。

> 换句话说：`out/` 能跑起来，靠的是那 60 个源码文件，不是它自己。源码在，云端随时能再生成一份。

#### 会推送的（60 个文件）

| 目录 / 文件 | 内容 | 数量 |
|---|---|---|
| `src/` | 页面、组件、样式、读取逻辑 | 34 |
| `content/` | 文章、纪录片、简历正文、模板 | 15 |
| 根目录配置文件 | `package.json`、`package-lock.json`、`next.config.mjs`、`tsconfig.json`、`.gitignore`、`README.md` | 6 |
| `public/` | `favicon.svg`、`.nojekyll` | 2 |
| `.github/workflows/deploy.yml` | 自动部署工作流 | 1 |
| `docs/使用说明书.md` | 本文件 | 1 |
| `scripts/serve-out.mjs` | 本地预览用的小服务器 | 1 |

**`content/` 里的 15 个文件**＝ 7 篇文章 + 1 个文章模板 + 5 部纪录片 + 1 个纪录片模板 + `pages/about.md`。模板虽然不会发布成网页，但它是你写新内容时的参照，应该留在仓库里。

两个容易漏掉的：

- **`package-lock.json` 必须推。** 它锁定了依赖的精确版本，保证云端装出来的环境和本地完全一致。别的项目里它常被忽略，这个项目不行。
- **`public/.nojekyll` 必须推。** 少了它，线上网站会完全没有样式（原因见 3.2）。

#### 不会推送的（已在 `.gitignore` 里排除）

| 目录 | 为什么不推 |
|---|---|
| `out/` | 构建产物，云端会自己重新生成 |
| `.next/` | 构建时的临时缓存，同上 |
| `node_modules/` | 依赖包，几百 MB，云端用 `package-lock.json` 自己装 |
| `.env` / `.env*.local` | 环境变量，可能含密钥 |

这四类都**不需要你手动做任何事**。`.gitignore` 已经写好了，`git add .` 会自动跳过它们。

#### 想自己确认一下

```bash
# 列出所有会被推送的文件（应该 60 个，且不含 out / .next / node_modules）
git ls-files | wc -l

# 检查某个目录是否被正确忽略（有输出 = 已忽略，正确）
git check-ignore out .next node_modules
```

#### 如果不小心已经把 `out/` 推上去了

```bash
# 从 git 里移除，但保留本地文件（注意是 --cached，没有 --cached 会把文件也删掉）
git rm -r --cached out
git commit -m "Stop tracking build output"
git push
```

推上去之后仓库会立刻瘦下来，不影响线上网站——线上那份 `out/` 是 Actions 生成的，和仓库里这份无关。

### 6.7 想用自定义域名

1. 在 `public/` 下新建一个文件叫 `CNAME`，里面只写你的域名一行，比如 `www.example.com`
2. 仓库 **Settings → Pages → Custom domain** 填同一个域名
3. 到域名服务商那里，把域名指向 GitHub Pages（顶级域名加 A 记录，子域名加 CNAME 记录，具体 IP 以 GitHub 文档为准）
4. 自定义域名总是从根路径提供服务，**所以不需要 BASE_PATH**（workflow 会自动判断，因为你此时通常会把仓库改名或直接用自定义域名访问）
5. 把 `src/data/site.ts` 的 `url` 改成 `https://www.example.com`

## 8. 常见问题排查

### 网站能打开，但完全没有样式（白底黑字）

**如果是本地**：你双击打开了 `out/index.html`。别这么干，用 `npm run preview`。

**如果是线上**：BASE_PATH 不对。去 Actions 日志里找「Work out the base path」那一步，看它输出的路径是否和你的网址前缀一致。普通仓库应该是 `/仓库名`，`<用户名>.github.io` 仓库应该是空的。

### 某个页面线上 404，本地却正常

GitHub Pages 的服务器**区分大小写**，Windows 本地通常不区分。检查链接里的大小写和实际文件名是否**完全一致**，包括扩展名。

### 构建报错 `is missing a required "title"`

`content/` 下某个 Markdown 文件 frontmatter 少了 `title` 或 `date`。错误信息里会写清楚是哪个文件。

### 新写的文章没出现

按顺序检查四点：

1. 文件名是不是以 `.md` 结尾
2. 是不是放在 `content/articles/`（不是 `content/pages/`）
3. frontmatter 里 `date` 有没有写
4. 是不是写了 `draft: true`

### 文件名以 `_` 开头的内容不会显示

这是**故意的**，用来把 `_TEMPLATE.md` 这类模板文件放在内容目录里又不被发布。想发布就去掉文件名开头的下划线。

### 标签页打不开

标签是自动汇总的，`/tags/<slug>` 里的 slug 是「标签名转小写、空格换成连字符」。`Field Notes` 对应 `/tags/field-notes/`。最可靠的办法是**从 `/tags` 页面点进去**，不要手打网址。

### 端口被占用

```bash
npm run dev -- -p 4321
npm run preview -- --port 4321
```

### 依赖装坏了 / 想重来

```bash
rm -rf node_modules package-lock.json
npm install
```

Windows PowerShell：`Remove-Item -Recurse -Force node_modules, package-lock.json`

### 想升级 Next.js

```bash
npm install next@latest react@latest react-dom@latest
npm run build
```

如果构建失败，把错误贴出来。本项目面向 Next.js 16，动态路由里 `params` 是按 Promise 处理的，这是 Next 15+ 的写法。

## 9. 留言板、背景音乐、小互动与彩蛋

这一章的每个功能都遵循同一条规则：**在 `src/data/site.ts` 里配置了才出现，不配置就完全不存在**。整个站已经默认开启的只有三个零配置的小互动（9.3）。

### 9.1 留言板（基于 GitHub Discussions）

留言板跑在 **giscus** 上：评论数据就存在你这个仓库的 Discussions 里。没有服务器、没有数据库、没有第三方账号体系——留言的人用 GitHub 账号发言，你用仓库就能管理（回复、删除、锁定都在仓库的 Discussions 标签页里操作）。

**开启（约 5 分钟，只做一次）：**

1. 仓库页 **Settings → General → Features**，勾选 **Discussions**
2. 打开 `github.com/apps/giscus`，安装 giscus 应用，权限只给这个仓库
3. 打开 [giscus.app](https://giscus.app)，填入你的仓库名，Discussion 分类选 **General**（或新建一个叫 `Guestbook` 的分类），页面会生成一段配置代码
4. 把代码里的四个值抄进 `src/data/site.ts`：

```ts
giscus: {
  repo: 'h-zhu/personal-site',     // 用户名/仓库名
  repoId: 'R_kgDOxxxxxxx',         // 生成的代码里 data-repo-id
  category: 'General',             // 分类名
  categoryId: 'DIC_kwDOxxxxxxx',   // 生成的代码里 data-category-id
},
```

四个值都填上之后，`/guestbook` 页面会自动从「配置指引」切换成真正的留言框。任何一个值为空，页面都会显示那三步指引——所以你随时可以只填一半，看看进展。

**关掉留言板**：把四个值清空即可，导航里的 Guestbook 链接如果你想连页面一起去掉，把 `nav` 数组里那一行删掉。

### 9.2 背景音乐（默认关，永远不自动播放）

1. 把音乐文件放进 `public/audio/`，比如 `public/audio/ambient.mp3`
2. 在 `src/data/site.ts` 里设置：

```ts
audio: {
  url: '/audio/ambient.mp3',  // 路径以 / 开头，指向 public/ 里的文件
  title: 'Background sound',
  volume: 0.4,                // 0–1，背景乐建议压低
},
```

之后每页右下角会出现一个小的 **Sound** 胶囊按钮：读者点一下开、再点一下关，选择会被记住，翻页不断。

**这是刻意的设计**：浏览器本来就禁止自动播放，文艺站也不该有突然响起的音乐——音乐永远是读者自己的选择。`url` 留空，按钮在所有页面上完全不渲染，就像这个功能不存在。

> **版权提醒**：放你有权使用的音乐——自己做的、免版权曲库（如 Pixabay Music、Free Music Archive）买的、或有授权的。GitHub Pages 是公开托管，放受版权保护的商业音乐有下架风险。

### 9.3 小互动（已开启，零配置）

| 互动 | 在哪 | 说明 |
| --- | --- | --- |
| 阅读进度线 | 文章、纪录片详情页顶部 | 一条 2px 的赤陶色细线随滚动变长，不挡内容 |
| Copy link | 文章标题下方 | 点击复制本文链接，2 秒后变回 |
| 返回顶部 | 左下角 ↑ | 滚过约一屏才出现，点了平滑回顶 |
| 页脚时钟 | 每页页脚 | 「It is 09:13 where H. Zhu is.」——读者知道你那边几点 |

时钟用的是 `site.ts` 里的 `timeZone`（IANA 时区名）。默认是 `Asia/Shanghai`，如果你在别处，改成自己的（查名字：Wikipedia 的 *List of tz database time zones*）。**留空字符串则时钟整个隐藏**。

### 9.4 彩蛋与版权页

**版权页 `/colophon`**——作家/导演个人站的传统：说明这站用什么字、怎么搭的。入口在页脚最右边，**故意做得很淡**（浅灰、平时几乎看不见，悬停才清晰）。内容在 `content/pages/colophon.md`，就是普通 Markdown，随你改写——包括最后一节提到的那个秘密。

**Konami 彩蛋**——在任何页面按 ↑ ↑ ↓ ↓ ← → ← → B A，屏幕会浮现一行字（默认是 *"For the people who let me point a camera at them."*，点一下消失）。这行字在 `site.ts` 的 `dedication` 里，改成你想留给「愿意多按几个键的读者」的话。**清空即禁用**。

> 版权页最后一节写了这个秘籍——藏起来的东西，在另一个半藏的地方留下说明书，这本身也是风格的一部分。

### 9.5 这一章涉及的所有文件

| 想改什么 | 改哪里 |
| --- | --- |
| 留言板四个配置值 | `src/data/site.ts` → `giscus` |
| 音乐文件与开关 | `public/audio/` + `src/data/site.ts` → `audio` |
| 时钟时区 | `src/data/site.ts` → `timeZone` |
| 彩蛋文字 | `src/data/site.ts` → `dedication` |
| 版权页内容 | `content/pages/colophon.md` |
| 留言/删留言 | 仓库的 **Discussions** 标签页 |
